# PLNT Planet Generator: Workflow Audit

*12 September 2026 · Blender 5.2.1 LTS · RTX 2060 6 GB / Ryzen 5 3600 / 16 GB · read-only, no code changed*

> **Status: answered by v3 on 13 September 2026.** This document is kept as the
> record of what was found and how it was measured. What was done about it, and
> which recommendations were adopted, rejected on measurement or deferred, is in
> `V3_REPORT.md`. Where the two disagree about a number, the v3 report is the
> later measurement and wins.

Anything marked **measured** was run on this machine today. Everything else is read from the graph and labelled as an estimate.

---

## 1. The verdict, in five lines

1. **The foundations are sound.** v2's closed-form atmosphere was the right fix, the tooling is verifiable (159 documented parameters, zero orphans, clean extension install, re-confirmed today), and the measurement discipline is unusually honest.
2. **The next render-time lever is the terrain field, not the clouds.** Three cheap changes measured today stack to roughly **half the shading time** on shot 02; the cloud-shadow refactor the README calls "the largest remaining opportunity" measured **no speed gain at all**.
3. **Memory, not speed, is what breaks low-end machines**, and Blender 5.0's object-space adaptive subdivision makes micropolygon memory independent of camera and resolution, which retires the "dice 2.0 or get OOM-killed" problem properly.
4. **The interactive experience is heavier than the render.** Each slider drag re-evaluates the field for 2.2 s, the viewport render is set to 1024 samples with denoising off, and the fastest displacement mode isn't even offered in the UI.
5. **Ship-blocking polish items exist**: the extension zip is stale (missing the lava-crust fix), "Randomise Section" can set the planet radius to ~50 000, and a second, older UI is still embedded in the .blend and registers under the same panel ID.

## 2. Where the time actually goes (shot 02, earthlike)

**Measured today**, paired, thermally gated, 960×540, 64 fixed samples, adaptive sampling and denoising off, GPU (OptiX). Each mutation ran against its own fresh baseline. Image mean is the degenerate-frame guard: unchanged means the mutation did not break the picture.

| mutation | what it tests | render time vs baseline | image mean | read as |
|---|---|---|---|---|
| `disp_true` | `displacement_method` DISPLACEMENT instead of shipped BOTH | **73.7 %** (-26 %) | identical | **biggest cheap win**; README estimated 10 % |
| `elev_single` | drop the 3-tap finite-difference slope (Eu/Ev) | **83.2 %** (-17 %) | +1.5 % | slope costs a fifth of shading; there is a free alternative (§3.2) |
| `detail_half` | halve noise `Detail` octaves in the field | **88.8 %** (-11 %) | identical | octaves below pixel size at hero distance |
| `noise3d` | 4D → 3D noise/Voronoi in the field | **87.8 %** (-12 %) | identical | the 4th dimension only carries the seed |
| `cloudshadow_off` | `PLNT_Clouds.visible_shadow = False` | **98.2 %** (-2 %) | +1.7 % | **inside the noise**: cloud shadow rays are not a cost |

Caveats: these three field mutations overlap (they all reduce field cost), so they do not add linearly. Baselines were 12.5-13.0 s of render time; the harness adds ~6 s of process startup that is excluded. Prior v2 numbers (atmosphere 54 %, clouds 30 %, shader 9 %) still stand.

**The structural cause.** `PLNT_TerrainFieldSH` calls `PLNT_ElevationSH` **three times** per shading point (E0, Eu, Ev) to build slope by finite difference. Each call is 5 noise + 1 Voronoi, all 4D. On top of that the surface shader carries 21 more 4D textures, and with `BOTH` displacement Cycles evaluates the displacement subtree **three extra times** per hit for the bump normal. That multiplication is where the render time is.

**Fixed cost matters for beginners.** Earlier today at 480×270 the GPU render was 10.3 s fixed + 6 ms/sample, so a 32-sample Quick Render is ~90 % fixed cost (geometry-node evaluation, BVH, kernel load), so pressing the button feels slow regardless of samples. Persistent data is off by design for the batch; it is the right thing to turn **on** for interactive use.

## 3. Recommendations, ranked by gain ÷ effort

### 3.1 Change the default displacement mode to GEOMETRY (*measured -26 %, effort: minutes*)
`core/lod.py` already has a GEOMETRY mode (`displacement_method='DISPLACEMENT'`, adaptive subdivision on). Make it the FINAL default and keep BOTH for ARCHIVE and the 200 mm close-up (shot 06). Re-check shot 06's detail ratio once; everything else is identical by image mean. **The UI `Displacement` enum does not list GEOMETRY at all** (`core/ui.py` offers NONE/MICRO/BUMP/TRUE): the fastest full-detail mode is unreachable from the panel.

### 3.2 Derive slope from the geometry normal instead of finite differences (*measured -17 %, effort: half a day*)
The globe is real displaced geometry, so the true terrain slope is already there: `slope = 1 - dot(N, normalize(P))` using the shading normal (Blender 5.0: `N` always includes displacement; `undisplaced_n` is also available). That removes Eu/Ev, two of the three field evaluations, and is exact at dice resolution. Keep finite-difference as an expert fallback for the ground patch, which is not a sphere.

### 3.3 Split the field into "per-vertex" and "per-pixel" halves (*estimate a further 10-20 %, effort: a day*)
Temperature, humidity, latitude, biome_id and habitability are low-frequency; only elevation, sea mask, river and ocean depth need per-pixel evaluation. `PLNT_GlobeRig` already stores `elevation` and `habitability` as attributes, so store the other slow masks too and read them with an Attribute node. Per-pixel cost drops to the 6 textures that actually need it. This is the "more nodes" change with the best payoff: it moves work from the shader (per sample) to Geometry Nodes (once).

### 3.4 Tie noise octaves to the quality preset (*measured -11 %, effort: an hour*)
Expose a single `Detail Octaves` multiplier on the field groups and let DRAFT/PREVIEW/FINAL set it (e.g. 0.5 / 0.75 / 1.0). Same trick, in GN, for the globe's `Subdiv Level` (7 for preview, 8 for final): **measured** GN evaluation 0.56 s vs 2.2 s per change.

### 3.5 Switch adaptive subdivision to Object space for low-memory mode (*effort: minutes, closes the OOM class*)
`PLNT_Adaptive.adaptive_space = 'OBJECT'` with `adaptive_object_edge_length` makes micropolygon count independent of resolution and camera ([5.0 notes](https://developer.blender.org/docs/release_notes/5.0/cycles/), [manual](https://docs.blender.org/manual/en/latest/modeling/modifiers/generate/subdivision_surface.html)). Memory becomes computable up front instead of discovered by a killed process. Keep Pixel space as the "hero" option. Also note `plnt_headless.py` still defaults `dice` to **1.0** in final mode, the exact value that killed shots 07-10, and only `render_all.ps1` papers over it.

### 3.6 Measure `emission_sampling` on a tech shot (*hypothesis, one paired run*)
`PLNT_Surface` has `emission_sampling = AUTO`. On Tech Level 0 the emission folds to zero and the globe is not a light; on shots 07-10 every triangle of a **1.97 M-triangle** mesh becomes a candidate mesh light for the light tree. Shots 08 and 09 were the two slowest v2 renders (7.3 and 6.0 min) and both are tech-heavy. `ablate.py` already has `emis_none`/`emis_front` mutations, which were only ever run on shot 02, where they cannot show anything. Run them on shot 08. City lights do not meaningfully illuminate anything at planet scale, so `NONE` is probably free.

### 3.7 Do the cloud-shadow refactor for the look, not the clock
Sharing `PLNT_CloudField` between the cloud shader and the surface (README plan) is still worth it (sharper, correctly-registered shadows and no drift between two copies of the maths), but budget it as a quality feature. **Measured** speed gain from removing the shadow rays: 2 %, inside the noise.

## 4. Low-resource machines

**Measured today**

| what | value |
|---|---|
| Host RAM, headless render, 960×540, dice 1.0 | 1.73 GB peak working set |
| Host RAM, headless render, 960×540, dice 2.0 | 1.41 GB peak working set |
| **Full hero render**, 2560×1440 / 1024 spp, dice **1.0** | 3.66 GB host · **2.56 GB VRAM** · 138 s |
| **Full hero render**, 2560×1440 / 1024 spp, dice **2.0** | 3.65 GB host · **1.29 GB VRAM** · 131 s |
| Blender GUI with the scene open | 2.76 GB working set, 2.4 GB VRAM |
| Viewport evaluated mesh (Subdiv 8 + subsurf viewport level 1) | 983 040 quads / 1.97 M triangles |
| CPU fallback, sampling cost (measured earlier today) | **14.2× slower** per sample than OptiX |

What to do about it, in order:

1. **Ship a "Performance" toggle with three positions**, Low / Balanced / High, that sets quality, displacement mode, dicing space/rate, globe `Subdiv Level`, noise octaves and denoiser device together. Today a beginner has to know six independent settings in two different places (N-panel and Properties ▸ Render) to make the scene fit their card. `render.py`'s `apply_quality` is 80 % of this already.
2. **Low = object-space dicing + GEOMETRY displacement + Subdiv 7 + CPU denoise.** That combination is predictable-memory and cuts per-change viewport lag 4×.
3. **Preview settings are wrong for everyone**: `preview_samples = 1024`, `use_preview_denoising = False`. Rendered-viewport mode is unusable on a low-end card at those values. 32-64 samples with preview denoising on gives live slider feedback and would make the Quick Render button largely unnecessary.
4. **Turn `use_persistent_data` on in the GUI** (not in the batch). Repeated interactive renders skip most of the ~10 s fixed cost.
5. **CPU-only machines are viable at DRAFT**: 50 % resolution and 64 samples is 1/64 of the FINAL sample load; with 14× slower sampling that lands near GPU-FINAL wall time. Make the device probe print a clear "rendering on CPU - expect N× longer" note instead of silently falling back.
6. **Dead settings**: since 5.0 the default volume integrator is unbiased null-scattering; `volume_step_rate` and `volume_max_steps` in `render.py`'s presets do nothing unless `volume_biased = True` ([manual](https://docs.blender.org/manual/en/latest/render/cycles/render_settings/volumes.html)). Harmless now that the atmosphere is a surface, but `--atmo volume` users will get no speed control from them.

## 5. Beginners and experts

**What already works well**: Basic/Advanced/All tiers, the eight-slider Quick row, search across panels, tooltips on every socket, per-section Randomise/Reset, state messages ("Tech Level is 0 - civilisation is switched off"), copy/paste as JSON, every operator undoable.

**What a beginner hits first**

| problem | evidence | fix |
|---|---|---|
| "Randomise" on the Terrain panel can set **Radius to ~36 000-64 000** | `randomize_section` samples every float socket around the middle 28 % of its interface range; `Radius` is 1-100 000, atmosphere `Inner/Outer Radius` and ring `Inner/Outer` are 1-1 000 000 | keep a per-socket "safe to randomise" flag in `params.py`; skip radii, seeds excluded from range logic |
| Feedback loop is a 10 s button press | Quick Render is ~90 % fixed cost | rendered viewport with sane preview settings (§4.3) |
| Two render-relevant places | quality/displacement in Properties ▸ Render, everything else in the N-panel | keep them there (Blender convention) but mirror a one-line "Performance: Low/Balanced/High" into the N-panel header |
| Nothing says how long or how much memory | none | print an estimate from resolution × dice × Subdiv; even a coarse "~2 min, ~3 GB" prevents most OOM surprises |
| The fastest full-detail mode is missing | UI enum lacks GEOMETRY | add it and make it the default |
| No first-run path | panel shows only "Create Planet System" | after creation, expand Preset + Quick and collapse the rest; one line: "Pick a preset, change the seed, press Quick Render" |

**What an expert wants**

- **Node-group interface panels.** `PLNT_SurfaceShader` exposes **43 inputs in one flat list** on the group node and in the material; the globe rig shows 13 in the modifier. Blender 4.0+ node groups support interface panels; none are used here. Grouping sockets into panels inside the node tree gives collapsible sections in the modifier, the material and the node editor for free, and `params.py` could be generated from the panel structure instead of maintained beside it.
- **Per-object LOD**: `lod.apply_mode` already works by label; expose it per object (globe vs patch) rather than one global enum.
- **User presets on disk.** The manifest requests the `files` permission "to save user presets", but no save/load exists, only a JSON text box. A `presets/` folder with save/load/overwrite closes the gap and honours the permission statement.
- **Keep the floats-as-toggles design.** Gating features on a float that Cycles constant-folds at 0 is the right call; do not convert them to booleans, just show a checkbox-style toggle in the UI that writes 0/1.

## 6. Do more with nodes

Ordered by how much Python it removes or how much render work it moves out of the shader.

1. **Field split (§3.3)**: biggest render effect, pure Geometry Nodes + Attribute node.
2. **Slope from normal (§3.2)**: deletes two group calls.
3. **Presets inside the rig.** Add a *Menu* input ("Planet Type") to `PLNT_GlobeRig` and drive terrain defaults through Index Switch nodes. Presets then work when the .blend is appended into a file **without the add-on installed**. Today `apply_preset` is Python-only. Shading presets stay in Python (materials cannot read a modifier's menu), which is a reasonable split.
4. **Gizmos** (Blender 4.3+, [manual](https://docs.blender.org/manual/en/latest/modeling/geometry_nodes/gizmos.html)): a Dial gizmo on sun azimuth/elevation, Linear gizmos on ring Inner/Outer and atmosphere Outer Radius. Beginners drag in the viewport instead of hunting sliders; the gizmo panel appears on the modifier automatically.
5. **Mark the rigs as assets** (`asset_mark` + catalog) and set `is_modifier` on the GN groups so they appear in the Add Modifier menu and the Asset Browser. Zero code, real discoverability.
6. **Ground patch**: `plnt_patch.py` still ends in a Realize Instances node for the scattered rocks, the same pattern the orbital rig removed. Keep them as instances and set material before instancing.
7. **Rings**: the 384×512 polar annulus (196 k verts) is generated per evaluation; with 5.2's field deduplication that is fine, but the `Angular Segments` default could follow camera distance the same way the globe does.
8. **Geometry Nodes on Empties** (5.2) means `PLNT_SunPivot`/`PLNT_SunDir` could carry a tiny GN modifier that outputs the sun vector as an attribute, but drivers still are the only way to get that into a shader, so this one is not worth doing yet.

Things I checked and would **not** change: the per-pixel evaluation of coastlines (the README's reasoning holds, since baking those to vertices quantises them), the analytic atmosphere, the instanced orbital library, `emission_sampling='NONE'` on the atmosphere, `caustics` off, `use_guiding` off.

## 10. The two symptoms you asked about: verified causes

### 10.1 Blocky road lights
**Cause (read from the graph, confirmed in render).** Roads are the *edges* of a Voronoi (`roadcells`, DISTANCE_TO_EDGE, scale 46, Randomness 1) sampled on the raw sphere position with no domain warp and a hard linear ramp 0→0.0075. Voronoi edges are straight polygon sides; three edges meet at every vertex, so distance-to-edge is small over a wider area there, producing the bright knots. And it is a *different* Voronoi from the one the cities come from (`citycells`, scale 27), so the network is a polygon mesh laid over the land that connects nothing; it is gated only on land + habitability, so it covers every habitable region.

**Prototype (rendered, shot 07 night side at full resolution).** Road = distance from the shading point to the *segment joining the two nearest city centres* (Voronoi F1 and F2 Position outputs, and the two nearest sites of any point are always neighbours, so this is the Delaunay road graph), smoothstep width 0.0045, gated on both endpoints being settled cells. Result: the polygon artefact is gone completely. With the strict both-endpoints gate at Tech 3 almost no roads remain, so the tuning still to do is: gate on one endpoint being a city plus habitability, width ~0.006, a gentle warp so roads are not dead straight, and fade with distance from the city. ~14 nodes; no measurable render-time change.

Related: `citycore` is a hard LINEAR ramp (0→0.30) → round blobs; give it a smoothstep and a second, coarser Voronoi so capitals are larger than towns.

### 10.2 The clear line on the horizon: two different lines
**Lit limb (your second crop): a hairline inside the atmosphere band, parallel to the horizon.** The analytic atmosphere evaluates *illumination* (`sun · normalize(P)`) at the shell hit point. Rays that hit the planet see one face of the shell; rays that just miss it see two, at different points with different sun angles, so brightness steps at the limb. **Prototype:** evaluate illumination at the ray's closest-approach point `C = P - (P·d)d` (the same point for both faces, and physically the densest part of the chord), and use the full alpha rather than the per-face split where only one face is visible. Rendered on a lit and a dark limb: the hairline is gone on the lit limb (crop on the review page); the disc's atmosphere brightens slightly, which is correct. Around a dozen nodes.

**Dark limb: bright spikes exactly at the horizon.** Not the atmosphere. Hiding `PLNT_Clouds` from camera removes them entirely (row profile 38/51 → 11/14) while hiding the atmosphere leaves them. It is the **cloud shell seen edge-on**: its Translucent BSDF is lit from behind by the sun and stacks up along the silhouette. Fix: multiply cloud alpha by a facing term (smoothstep of |N·V|, 0→0.25) or drop the Translucent share at grazing angles.

## 11. UI and UX, round two: from the live panel

The panel screenshot is on the review page. Findings in severity order:

1. **Every modifier-backed control is broken on 5.2.** Seed, Continent Scale, Sea Level, Relief Strength, Orbital Level and every Terrain / Orbital / Megastructure / Ground Patch / ring-rig / cloud-rig / atmosphere-rig socket draw as the text **"ID Property Group"** instead of a slider. Blender 5.2 changed the modifier API: inputs are now RNA structs (`modifier.properties.inputs.<id>.value`); see [5.2 Python API notes](https://developer.blender.org/docs/release_notes/5.2/python_api/). `draw_socket` does `layout.prop(holder.properties.inputs, '["Socket_N"]')`, which now points at the group, not the value. Fix: `layout.prop(holder.properties.inputs[ident], "value", text=…)`. The write paths (`gset`, `_set_mod_inputs`) already handle the `["value"]` form, which is why presets work while sliders do not. Only material-backed controls (Tech Level, Cloud Coverage, Density) work today.
2. **Opening the shipped .blend gives users the v1 panel, not the extension.** The `PLNT_presets.py` text block auto-registers `PLNT_PT_main` + four sub-panels on load. The extension's panels share that `bl_idname`; `ui.register()` swallows the failure and the mixed result is whichever loaded first. Strip the UI classes from the text block (keep the preset table).
3. **The preset dropdown does not show the current preset.** It defaults to the first alphabetical entry ("Colonial Outpost") while the scene is Earthlike. Write `scene.plnt.preset` from `apply_preset` and show "modified" when any value differs.
4. Labels truncate at the default sidebar width ("Contine…", "Relief St…"). Shorter display names for the Quick row, or `use_property_split`.
5. The 13 collapsed sub-panels are a flat list. For beginners group them into four (Planet · Sky · Civilisation · Scene) and let node-group interface panels drive the grouping.
6. Add a **Time Scale** control to the Quick row (see §12). It is the one animation control everything else should hang off.
7. **Add a Quality dropdown to the Quick row whose lowest tier is a sub-minute render.** Measured today on shot 02, headless, OptiX, wall-clock including Blender start-up:

## 12. Animation: realistic motion and a single speed slider

**Current state (measured):** nothing moves. Frame range 1-250 at 24 fps is the default; no object has keyframes; there are no Scene Time nodes and no `frame` drivers; the only drivers in the file are the twelve sun-direction drivers. Hidden blocker: every shader compares an **object-space** position against the sun vector in **world space** with no Vector Transform node, so rotating the globe or cloud object would rotate the day/night terminator, the city lights and the atmosphere lighting along with it. Before anything animates, transform the sun vector World→Object (one node per shader) or rotate the sun pivot instead of the planet.

**Design: one slider.** `Time Scale` in hours of world time per second of footage (0 = frozen; presets 1 h/s "day in 24 s", 0.1 h/s "slow", 6 h/s "timelapse"). A `PLNT_Time` value = frame ÷ fps × Time Scale feeds everything, so a single slider keeps all motion mutually consistent. Rates in physical units, R = planet radius, Earth-like day length exposed as `Day Length` (h, default 24):

| element | realistic rate | how |
|---|---|---|
| Planet rotation | 360° / Day Length (15°/h) | object Z rotation, or shader-space rotation of the field coordinates |
| Cloud deck | planet rate + zonal drift 1-2°/h (jets ~50 m/s on a 40 000 km circumference) + slow morphing (advance the 4D `W` by ~0.02/h) | cloud object rotation; `W` driven from `PLNT_Time` |
| Atmosphere shell | static (spherically symmetric) | none |
| Satellites (shell 1.0-1.16 R) | Kepler: T = 84.5 min × (r/R)^1.5 → 90-110 min, i.e. 200-240°/h, each on its own inclined plane | GN: rotate each instance about its own random axis by ω(r)·t |
| Orbital bands at 1.24 / 1.34 / 1.46 R | if orbiting: 185 / 165 / 145 °/h. If they are *stationary rings* (active support) they do not move, so expose a toggle | GN rotation of the band group |
| Space elevator | locked to the surface | rotates with the planet exactly |

## 14. Your comments on the review page, answered

Three threads were left on the Hero Sheet (none was sent to Claude, so they stay open there; this is the reply).

**Shot 09: "big white spots on the surface are what? more detail and more colour variation."** They are settlement cores: `citycore` is the Voronoi F1 distance thresholded 0→0.30 with a linear ramp, so every city is a round blob of the same size, and at Tech 9 the light colour is 85 % towards a single cool white. Fixes, cheapest first: (a) smoothstep the core and modulate its radius per cell by the Voronoi colour so cities vary 3-4× in size; (b) mix three light colours (sodium 2700 K, mercury/LED 4500 K, cool 6500 K) per cell from the Voronoi colour channels instead of one global `Light Colour Temp`; (c) raise the sprawl noise's contribution so cores break into districts; (d) a second, coarser Voronoi for a handful of capitals with a warmer, brighter centre. Real night-side imagery has exactly this hierarchy: a few large warm cores, many small ones, and colour that varies by region.

**Shot 08: "orbital rings are mostly white… some reflective parts, more detail, more protrudy bits, kitbashed style."** The hull material is *defined* near-black (base 0.022) but **Metallic 0.85 at Roughness 0.30**, so every sun-facing face is a specular reflection of a strength-4 sun, which AgX renders as flat white. That is why the bands read as white plastic. Recommended: a matte dielectric base (grey-white MLI, roughness 0.6) as the default, with metallic/reflective panels selected per instance from Object Info › Random (say 25 %), gold-foil patches and dark radiator panels as further random selections, and dirt/streak variation from a Noise in Generated coordinates. For "protrudy bits": a greeble pass in `core/orbital.py`, using Distribute Points on Faces over each module with density by face area, instance a second small-parts library (antenna masts, dishes, tanks, boxes, radiator fins) with random scale/rotation, then instance the greebled module as before. That is a few dozen unique triangles per part, still instanced, so it costs almost nothing. Also: `Light Material` on the rig is currently set to `PLNT_Orbital` (the hull) rather than `PLNT_OrbitalLight`, so the emissive window strips never use their intended material.

**Shot 04: "the satellites need more detail."** Same library and same material as above, so the same two fixes apply; in addition give satellites solar-panel wings (thin dark-blue flat grids on a boom, the single most recognisable satellite silhouette), a dish or two, scale variety of 4-6×, and darken the hull so only sun-catching panels flash. At Orbital Level < 2 also halve Module Scale so they read as points with the occasional glint rather than flakes.
